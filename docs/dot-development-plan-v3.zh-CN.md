# dot 网页桥接版开发计划 v3

2026-10-20。当前有效计划。用户说明 dot 也有输入框，因此本版转为在 aichat-bridge 现有网页桥接架构中支持 dot 网页，不开发 MCP Events companion。v1/v2 均为历史方案，不能作为当前实施说明。

## 1. 目标和范围

- 保留既有 ChatGPT、Claude、Gemini、Qwen 与群聊定制功能，增加独立的 dot 网页 provider。
- 沿用现有扩展的配置、网页绑定、任务调度、消息发送、恢复和错误提示机制；不创建 dot 模型 API，不要求独立服务器/tunnel/事件订阅。日常使用必须仍然只是浏览器扩展，不引入 Node companion、额外后台脚本或外部事件服务。
- dot 消息范围继续以本人私聊为保守目标，不因为增加网页 provider 就自动把群内容送入个人 dot；QQ 侧需要的范围和适配在网页可行性确认后同步审阅。
- 不自动登录、不读取 Cookie、不存账户密码、不创建 dot 或更改其设置。

## 2. 必须先取得的页面证据

目前没有已登录的真实 dot 网页 DOM 证据，禁止猜测 CSS 选择器、URL 路由或宣称现有 ChatGPT 适配器已经兼容。

需在用户授权的已登录浏览器中，确认真实 dot 的会话路由、输入框、发送入口、消息角色/稳定 ID、回复状态、完成/失败/停止状态、历史加载与导航行为。只读取完成判断所需结构，避免保存用户的私人对话全文。

观察完整流程：发送一条受控测试消息、模型开始回复、增量生成、连续多条回复、显式完成或其他可可靠判断的终态。真实发送测试需有用户对这次测试的授权，不能把页面检查授权当成发消息授权。

## 3. 设计约束

1. dot 独立于普通 ChatGPT provider，不能仅替换显示名称或 URL。
2. 使用实际 DOM 证据决定选择器；优先语义/可访问性定位与稳定属性，保留页面改版时的明确失败提示。
3. 回复关联必须锚定本次成功提交的用户消息及其后继回复，不能拿“最新一条助手消息”作本任务结果。
4. dot 可能连续发多条，也可能夹杂与任务无关的主动消息。必须识别可验证的 turn/消息关联及终态；不得靠简单 idle timeout 就断言回复完整。
5. 若页面不提供可靠关联或完成信号，先标记功能受限或等待人工确认；不能用计时器拼凑“已完成”、漏回多条或串入私人主动消息。
6. 发送前后检查会话身份、导航、取消及已有在途任务；未知提交结果不自动重发。关闭/刷新、重连和重复点击应可明确恢复或安全停止。
7. 保持 provider 和平台隔离，不自动扩展群聊权限或上传上下文。

## 4. 实施顺序

A. 先提交本计划；归档已暂停的 event/C2C 草稿，恢复扩展基线。
B. 取得并审阅真实 dot DOM/生命周期证据，说明可支持的消息及完成检测范围。
C. 证据足够才实现 provider、配置/绑定入口及有限范围回传；若证据不足，只报告具体阻塞及最小下一步，不提交假实现。
D. 从脱敏结构制作离线 DOM fixture，覆盖多条回复、无关主动消息、重生成/停止/失败、历史加载、导航、重复发送和恢复等情况；运行原全套回归。
E. 经用户授权做最小真实端到端验收。离线通过、真实已验证、仍待验证必须分别报告，最后再打包提交。
