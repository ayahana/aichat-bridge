# dot 本人私聊版开发计划书

状态：计划先行，等待审阅；本提交没有实现代码。日期：2026-10-20。

## 1. 基线与目标

- 基于 `aichat-bridge` 定制群聊版提交 `c7a77cce2a321b6189902474b1ed75f51fb63ca1`，独立分支 `feat/dot-owner-private`。
- 保留现有 ChatGPT / Claude / Gemini / Qwen 网页桥接，以及已有 QQ 群聊功能。dot 是独立服务提供方，不冒充第五个网页，也不把普通 ChatGPT 回答伪装成现有 dot。
- 本轮 dot 仅接本人 QQ C2C 纯文字：认证 QQ 网关 → 主人过滤 → 持久消息队列 → 已授权 MCP Events 回调 → 现有 dot → 受限回复工具 → 同一个主人私聊。
- 不支持 dot 群聊、陌生人、频道、入站附件、任意收件人或任意 URL；不创建真实账户、凭据、隧道、订阅，不安装部署，不实际收发 QQ。

## 2. 已确认的技术依据与复用

1. 官方协议：<https://developers.openai.com/plugins/build/mcp-events>。采用 `server/discover`、`events/list`、`events/subscribe`、`events/unsubscribe` 和签名回调；不存在本项目可直接调用的“dot 模型生成 API”。事件送达 ACK 不等于 dot 已处理或 QQ 已发出。
2. 参考实现：<https://github.com/Arcueid77/dot-qq-bridge>，固定提交 `b403176c980d460ecffa87dcd722dd8740fb6c37`。其项目 MIT 许可可用于复用，保留 A2KT 版权、许可证及来源清单。优先复用并审查现成认证、QQ 网关、SQLite 状态机、回调传输和 tunnel adapter，不另写一套安全协议。
3. 该参考的 `@dot-bridge/core@0.2.1` 固定发行包来源 revision `fac9d7d05b6c0a5da20411d20963af5eb9c456fc`、SHA-256 `3f1c77376002432ebc748e4f32eeb559684b93a812c85e29cb0e16e43f02842a`；实施前检查内含许可与模块边界，固定版本及完整性。
4. 参考的 `@tencent-connect/qqbot-connector@1.2.0` 标为 UNLICENSED。本版不复制、打包、依赖或运行该扫码组件；只接受操作者另行合法取得并授权使用的凭据文件。复用范围排除自动扫码、凭据创建和部署脚本。
5. <https://github.com/AnctyEnly453/qq-dot-bridge> 仅作协议/网关参考，不将其作为自动 LLM 或现有 dot 的替代品。

## 3. 架构与信任边界

### 3.1 独立 DotProvider 与 companion

- 新增独立 `companion/` Node.js 包及明确的 DotProvider 门面，封装固定上游模块与受限 QQ adapter。浏览器不接触 dot 授权、签名秘密、加密密钥或 tunnel service key。
- 复用原扩展的产品入口/说明风格，但不把服务器 SDK 放进 extension，不增加 localhost / 全域访问权限，不让 DOM 轮询触发 dot。
- 页面入口显示真实部署前置条件及离线状态，不设置一个看似可用、实际不会回复的开关。是否需要最小状态入口在代码审阅后决定，实际消息链始终在 companion。
- 私有 Secure MCP Tunnel 只给本人使用：所有 Tunnel Use 持有者具有本地服务权限，因此不能通过群共享、开放公网匿名入口或任意客户端身份字段来认定主人。

### 3.2 单一 QQ 网关所有权

- 默认要求 dot 使用专用 QQ Bot App ID，和现有网页/群聊机器人分开。现有扩展所有 profile 保持自己的身份保留规则。
- 如复用原 App ID，必须先关闭其全部扩展连接并移除/停用旧部署，确认完全退出后才启动 companion；不能边切换边运行。
- companion 启动时持有 App ID 对应私有互斥锁；停机先停止接收、等待在途操作、关闭网关/数据库后才释放。崩溃锁不自动抢占，人工核实无旧实例后恢复。
- 同机锁不能检测另一电脑或未协调的旧扩展，这是明确限制；不承诺跨主机互斥。文档和启动预检要求操作者确认专用账户/唯一消费者，避免用空泛的“自动锁”掩盖风险。

### 3.3 安全与耐久性

- MCP 路径强制已认证、固定 owner principal；消息仅接受 QQ 认证网关中的绑定 owner，拒绝其他 peer / 群 / 附件。回复工具仅用服务端消息 ID 派生目标，禁止调用者传收件人。
- 订阅只允许 owner 过滤器、一个有效订阅代次；校验 whsec 密钥长度、HTTPS allowlist、公网 DNS/IP、TLS 主机名、禁止重定向；签名 challenge 回显常量时间验证后才接受订阅。
- 发送回调使用标准 webhook ID/timestamp/签名及订阅 ID；测试接收端校验错误签名、过期时间和重放。注意回调签名由 ChatGPT 接收端校验，本服务不是伪造一个接收 dot 回复的 webhook。
- 队列有容量、正文、速率、保留时间、订阅和被动回复截止限制；先持久提交再确认入站。重复消息、重复工具调用、并发调用、恢复后的状态必须幂等。
- QQ 发出后超时/崩溃且 ACK 不明进入 uncertain，不能自动重发。回调事件重试与 QQ 回复重试分开处理，回调保留相同事件 ID，限制次数和期限。
- 记录接收、排队、回调 ACK、dot 开始处理、回复排队、QQ ACK 的阶段耗时；日志不含正文、完整 URL、凭据、owner 标识。没有观测到的阶段不可虚报耗时或“已连接”。

## 4. 开发阶段（计划审阅后才开始）

1. 固定许可及来源，建立可独立安装的 companion 包、DotProvider 门面和离线配置预检，拒绝默认启动真实外连。
2. 复用审查过的 QQ / MCP / 持久队列实现；限制到 owner-only tunnel 模式，移除不需要的 Sites、扫码和部署入口。确保必要依赖闭包完整、许可齐全。
3. 接入生命周期、单消费者声明、阶段诊断；原网页/群聊路径不变。补中文使用说明、部署条件和故障恢复手册。
4. 运行原扩展全套检查及新服务离线测试。增加跨边界合约测试：伪认证、错 owner、错签名、SSRF、重放、队列满、订阅撤销/过期、回复过期、重启、uncertain、重复发送、锁争用、日志脱敏。
5. 打包源码（排除 node_modules、真实配置、数据库和密钥），提交精确验证报告。父级独立审阅后再按其授权处理远端发布，本任务不 push。

## 5. 部署前提与尚需实证

开发交付不等于已经可直接使用。实际使用至少需要：Node 24.15 至 24.x、支持私有文件权限的宿主、持久私有磁盘、本人 QQ 官方机器人资格及合法凭据、已核实 owner ID、私有 tunnel 与仅本人可用的 MCP/plugin、明确授权的 callback 主机和订阅，以及后台 supervisor。首次存凭据、授予长期访问/增加权限、创建订阅都需要操作者另行参与。

必须在独立验收中证明：真实 dot 能发现工具和事件、正确订阅和续期、QQ 本人消息触发的确是原 dot、回复只到原私聊、陌生人/群被过滤、短答/长答/连续消息正确、断线与进程重启不重复、被动回复窗口与限流符合实际账号、撤销立即停止、关闭浏览器后服务生命周期符合预期。当前无真实凭据，不以 mock、历史上游报告或一次 ACK 代替上述实测。

## 6. 本阶段审阅检查点

本计划提交只声明目标，不声明测试通过。实现前由父级审阅：独立 companion 而非 DOM provider；采用固定许可可用模块；dot 私聊与现有群聊分离；默认离线；单网关部署边界明确；测试与真实验收分开。
